# vmx-rs wgpu エンコード/デコード 最適化監査（2026-11）

対象: `vmx-rs` v0.2.3（`main` / commit `e6c7373`）  
監査環境: Apple M3 / macOS 27.2 / arm64 / wgpu 30.0.1 / Metal / 8 threads  
比較用の離散 GPU 数値: リポジトリ内 `BENCHMARK.md` の NVIDIA L4（Vulkan）結果  
実装結果: [`IMPLEMENTATION-2026-11.md`](IMPLEMENTATION-2026-11.md)

---

## 0. 結論（要約）

1. **vmx-rs の更新**は完了した。`perf/hot-path` は上流でマージ済み・削除済みだったため、
   ローカル `main` を `f1fd18b` → `e6c7373`（v0.2.3）へ fast-forward した。
   `cargo test --features wgpu` は全テスト成功（`settle_q` は debug だと非常に遅いので
   release で実行し 1.78 s で成功）。

2. **Lean は「どこが速いか」も「十分に最適化されているか」も判定できない。**
   Lean ができるのは「この書き換えは出力を変えない」ことの機械検証である。
   今回もその用途で使い、以下を証明した。
   - zigzag の順列性と encode/decode の往復
   - 現行 32 B 係数パックが**いつ損失になるか**（係数 31 以上、i8 範囲外）
   - float の `/16.0` と整数 `>>4` が負の非 16 倍数で一致しないこと
   - i16 飽和を省けないこと
   - shared memory の stride 9 が bank conflict しないこと
   - 16×8 encode tile のテクスチャ読み出しが現行 512 回 → 全融合 128 回になること

3. **現状の wgpu パスは「転送を避ける」設計としては良いが、カーネル単体の最適化は
   まだ余地が大きい。** 測定できた改善は以下。
   - decode シェーダ: **3.01 ms → 2.42 ms（約 20% 減）**、PSNR は現行と同一
   - encode シェーダ: **opaque 3.73 ms → 2.91 ms（約 22% 減）**、
     alpha 5.21 ms → 3.58 ms（約 31% 減）、PSNR 100 dB（CPU と一致）を維持
   - ただし M3（内蔵 GPU）では、それでも CPU の方が速い:
     decode は CPU 1.12 ms / CPU+upload 1.78 ms に対し GPU 2.42–3.01 ms、
     encode は CPU 1.26–1.60 ms に対し GPU 2.91–3.58 ms。

4. **最大の問題は性能ではなく decode の非可逆性。**
   現行 `decode_to_texture` は係数 31–63 を捨て、AC を i8 に clamp し、
   float IDCT で計算するため、CPU デコードと一致しない
   （1080p natural / OMT_SQ で PSNR 39.82 dB、max abs 33）。
   全 64 係数 i16 + 整数 IDCT + DC-only フラグにすると **PSNR 100 dB（0 diff）** で
   一致することを実験で確認した。ただし M3 では 6.40 ms と遅い。
   用途に応じて「高速・非可逆」と「正確・低速」を分けるべきである。
   実装後の Exact は、最適化シェーダでは 1080p で 3.55 ms（Fast 2.50 ms）まで
   縮んでいる。

5. **実用上の最大の改善はアダプタ依存の経路選択。**
   - 内蔵 GPU（Apple M3 など）: CPU の方が速い。GPU はテクスチャが既に GPU 上に
     あり、readback を避けたい場合だけ有利。
   - 離散 GPU（L4 など）: GPU は「CPU + texture transfer」には勝つが、
     host CPU 単体には負ける（encode は顕著）。GPU の価値は転送回避である。
   - したがって `device_type` / `is_integrated` / 解像度 / テクスチャの所在で
     自動選択する API を追加すべき。

## 4. 現状できている最適化（評価できる点）

- decode は 1 回の compute pass で IDCT + 4:2:2→BGRA を融合している。
- `BGRA8UNORM_STORAGE` があれば buffer→texture copy を省いて直接格納する。
- encode は compute で FDCT + quant + zigzag まで行い、Golomb だけ CPU に残す。
- encode の UBO / 行列 / テーブルは変化時だけ `write_buffer` する。
- decode の行列も変化時だけ更新する。
- encode の readback は 3 スロットの ring を使い、`map_async` + submission index wait で
  キュー全体の待ちを避ける。
- `encode_from_texture_submit` / `encode_submitted_finish` で
  GPU FDCT と CPU Golomb を分離できる（パイプライン化の土台がある）。
- 係数パックは 32 B/block と小さく、decode の upload 帯域を抑えている
  （ただし非可逆）。
- `VMX_GPU_TRACE` で `golomb_pack` / `dispatch` / `encode_submit` / `encode_finish`
  の内訳を出せる。

## 5. 問題点と最適化余地

### 5.1 decode の非可逆性（P0: 正確性）

現行の係数パックは `src/gpu/pack.rs` の 32 B:

```text
i16 DC + i8 AC[1..30]   （係数 31..63 は捨てる）
```

`src/codec/plane.rs:277` で `temp_block[i].clamp(-128,127)` を i8 で書き、
`src/gpu/shaders/decode.wgsl:88` の `load_coeff` は `zig > 30` を 0 にする。
さらに IDCT は f32 で、CPU の i16 飽和・算術シフトと一致しない。

測定結果（1080p natural）:

| 方式 | PSNR | max abs |
|---|---:|---:|
| 現行（32 B + float IDCT） | 39.82 dB (q95) | 33 |
| 全 64 i16 + float IDCT | 52.38 dB | 7 |
| 全 64 i16 + 整数 IDCT + CPU も full IDCT | **100 dB** | **0** |
| 全 64 i16 + 整数 IDCT + DC-only フラグ | **100 dB** | **0** |

高 AC の影響:

| q | 高 AC（31..63）が非ゼロの block | i8 範囲外の AC |
|---|---:|---:|
| 92 | 13.9 % | 0 % |
| 95 | 48.2 % | 0 % |
| 96 | 56.2 % | 0 % |

自然画像 q92–96 では i8 溢れは 0 % だったが、高 AC は q95 で約半分の block に存在する。
したがって「31 以降を捨てる」ことが主因で、i8 clamp はコンテンツ次第の副因である。

**正確版の設計（実験で PSNR 100 dB を確認）:**

- 132 B/block: 64 × i16（zigzag 順） + u32 フラグ
- フラグ = CPU の `valid == false`（AC が全部 0 で `broadcast_dc` を使う block）
- シェーダはフラグ時だけ `(dc + 4) >> 3 + add_val` の broadcast を行い、
  それ以外は整数 IDCT（i16 飽和 + `>>11` / `>>6`）
- これで CPU の既定経路と 0 diff になる

ただし M3 では 6.40 ms（最適化前シェーダ）と遅い。正確性が必要な場合の
トレードオフを API で選べるようにするのがよい。

**提案:**

1. `decode_to_texture` を「高速・非可逆」と明示し、`decode_to_texture_exact`
   （または `GpuDecodeMode::{Fast,Exact}`）を追加する。
2. Exact は上記 132 B パック + 整数 IDCT + DC フラグ。
3. 中間案として「32 B 基本 + 高 AC がある block だけ tail」の hybrid pack。
   q95 なら 48 % の block だけ tail を読むので、全 132 B より帯域を抑えられる。
4. README / rustdoc に PSNR の実測値を載せ、「CPU と一致しない」ことを明記する。
5. `tests/gpu.rs` の decode は PSNR 28 dB しか要求していない。
   Exact モード追加時に `assert_eq!` の回帰テストを入れる。

### 5.2 decode シェーダの構造（P1: 速度）

現行 `src/gpu/shaders/decode.wgsl` の主な非効率:

- `sm` は 8 float/row（stride 8）。32 bank に対し `t*8 mod 32` は 4 値しかなく、
  同じ列を書くスレッドが conflict する。
- 行テーブル選択 `idct_tab(row, i)` を 16 回呼び、毎回 `switch` する。
- 出力は 32 スレッド中 16 スレッドだけが 8 行ずつ担当し、残り 16 は idle。
- 係数ロードは 8 係数ごとに `load_word` を呼び、`plane` 分岐と word 再計算がある。
- 行列 `matrix[i]` を storage から係数ごとに読む。

実験した改善（PSNR は現行と同一の 39.82 dB）:

1. `sm` を 4 block × 8×9 = 288 float に padding（stride 9）。
   `t*9 + k mod 32` は全単射なので conflict しない（Lean で証明）。
2. 行テーブルをスレッドごとに 1 回だけ選び、`idct_row` に配列で渡す。
3. 出力を 32 スレッド × 4 行に変更（`row_group = lid/16`、`lx = lid%16`）。

結果: **3.01 ms → 2.42 ms（約 20 % 減）**。

追加で効く可能性があるもの:

- `plane`/`block` から `base` を 1 回計算し、`load_coeff` に渡す。
- 32 B パックなら 1 block = 8 word。1 スレッド 1 行なら 3 word をまとめて読み、
  8 係数を抽出する（現在は最大 8 word を個別に読む）。
- 行列を `var<uniform>` または workgroup shared に置く（64 i32）。
- 64/128 スレッドで 2 tile を 1 workgroup にまとめ、barrier 回数を相対的に減らす。
- exact 版では 132 B なので `array<vec4<u32>>` にして 4 word を vector load する。

### 5.3 encode シェーダのテクスチャ読み出し（P1: 速度）

16×8 luma tile あたりの現行読み出し:

| plane | 読み出し |
|---|---:|
| Y（2 block × 64） | 128 |
| U（8×8 chroma × 2 pixel） | 128 |
| V（8×8 chroma × 2 pixel） | 128 |
| A（2 block × 64） | 128 |
| 合計 | **512** |

16×8 の元 pixel は 128 個なので、**4 倍の重複読み出し**がある。
`sample_u` と `sample_v` は同じ 2 pixel を読み、`sample_y` と `sample_a` も
同じ pixel を読んでいる。

実験した改善（PSNR 100 dB を維持）:

1. FTAB と ZIGZAG を storage から const 配列に移す（block あたり 320 load を削減）。
2. `fdct_quant_from_rows` の `cols` / `spatial` を廃止し、`rows` を in-place、
   量子化を row ごとに行う（4 × 64 i32 → 2 × 64 i32）。
3. `fdct_ya`（Y+A を 1 回の load で）と `fdct_uv`（U+V を 1 回の load で）に統合。
   4 dispatch → 2 dispatch、読み出し 512 → 256。

結果:

- opaque: **3.73 ms → 2.91 ms（約 22 % 減）**
- alpha: **5.21 ms → 3.58 ms（約 31 % 減）**

次の一手:

- **16×8 macroblock 全融合**: 64 スレッドで 128 pixel を 1 回だけ load し、
  Y/U/V/A を shared memory に展開。6 block を 8 スレッドずつで FDCT。
  読み出しは 512 → 128（4 分の 1）。Lean で `512 = 4 × 128` を証明済み。
- `load_rgba` の `min(px, width-1)` / `min(py, height-1)` を interior tile では省略する
  （edge 専用 pipeline か uniform flag）。
- encode matrix を storage から uniform / shared に移す。
  192 load/block を削減できる。品質プリセットごとに pipeline を specialize すれば
  行列を定数化して乗算まで畳める。
- 係数書き込みを `array<vec4<u32>>` の 8 vector store にする。
- per-thread の 8×8 block 計算をやめ、workgroup 内で 8 スレッド/block に分散する。
  現在は 1 スレッドが 64 i32 の配列を複数持ち、register/local memory 圧が高い。

### 5.4 encode の readback / パイプライン（P1: スループット）

`encode_from_texture` は submit → finish（map wait + CPU Golomb）を同期で行う。
`encode_from_texture_submit` / `encode_submitted_finish` を使えば分離できるが、
`coeffs` が 1 本しかないため、次の submit が前の finish を待つ。

提案:

- `coeffs` を 2–3 本の ring にし、slot ごとに bind group を持つ。
- `PendingGpuEncode` を queue にし、`encode_submitted_finish` が最古の slot を map する。
  これで frame N の CPU Golomb と frame N+1 の GPU FDCT が重なる。
- `coeff_read` の ring は既にあるので、出力先を ring に直接する（copy を 1 回減らす）
  か、少なくとも submit を塞がない。
- 8.4–12.6 MB/frame の readback は、内蔵 GPU では GPU 計算より小さいが、
  離散 GPU では PCIe 帯域が効く。exact にするなら hybrid pack も検討。

### 5.5 テクスチャ / bind group / pipeline の生成コスト（P2）

- `decode_to_texture` は毎 frame `make_bgra_texture` + `create_view` +
  `create_bind_group` を行う。
- `encode_from_texture_submit` は毎 frame `create_view` + `create_bind_group` を行う。
- `GpuSession::new` は codec ごとに shader module / pipeline を作る。
  複数 codec を持つアプリでは起動時ヒッチとメモリ増になる。

提案:

- decode は N 枚 ring の texture/view/bind group を事前生成し、
  `decode_to_texture_into(&Texture)` も用意する。
  API の「texture は再利用しない」契約は ring の寿命管理で維持できる。
- encode は caller の `TextureView` を受ける API、または texture を key にした
  bind group cache を用意する。
- `GpuContext`（device ごとの pipeline/layout キャッシュ）を共有する。
- `GpuSession` に `wgpu::Device` を保持し、`ensure_gpu` で device も比較する。
  現状は width/height しか見ていないため、別 device を渡すと古い resource を使う。

### 5.6 readback / preview / API（P2）

- `read_texture_bgra` は `wait` → `map_async` → `wait` と 2 回待つ。
  `map_async` を先に発行し、submission index の wait 1 回でよい。
- `decode_preview_to_texture` は実は CPU decode + `write_texture` であり、
  GPU パスではない。M3 では 0.60 ms で、CPU+upload の 0.21 ms より遅い。
  L4 でも 0.80 ms vs 0.71 ms で負ける。名前を変えるか、
  DC 係数から直接描く本物の preview shader にするか、CPU 経路に寄せる。
- `decode_preview_to_texture` は毎回 texture を確保して空 submit する。
  preview 用の persistent texture を再利用する。
- sRGB texture は `can_sample_encode` が false になり CPU fallback する。
  これは正しいが、理由を rustdoc に書く。
- `request_headless_device` は `Limits::default()`。8K alpha の係数 buffer は
  128 MB を超える可能性がある。8K を対象にするなら limit を確認する。

### 5.7 テスト / 観測性（P2）

- encode は実測 PSNR 100 dB（0 diff）なのに、テストは 35 dB しか要求していない。
  対応形式では `assert_eq!` にする。
- decode は 28 dB しか要求していない。lossy を仕様とするなら、
  期待 PSNR を明示し、exact モードのテストを追加する。
- `VMX_GPU_TRACE` は有用。`golomb_pack` / `dispatch` / `map_wait` / `entropy` を
  常時取得できる `GpuStats` を API にすると回帰検出しやすい。
- `settle_q` は debug で非常に遅い。release 実行を CI に入れるか `#[ignore]`。

## 6. Lean による検証

場所: `verification/lean/VmxGpu.lean`（Lean 4.36、Mathlib 不要）

```bash
cd verification/lean
lake env lean VmxGpu.lean
```

証明した内容:

| 定理 | 内容 |
|---|---|
| `zigzagInv_zigzag` / `zigzag_zigzagInv` | `ZIGZAG` と `ZIGZAG_INV` が 0..63 の逆順列 |
| `zigzag_roundtrip` | encode の zigzag 書き込み → decode の読み出しが恒等 |
| `gpuCoeff_exact_of_in_range` | DC または 1..30 かつ i8 範囲内なら現行パックは無損失 |
| `gpuCoeff_drops_high_ac` | 31 以上の非ゼロ係数は失われる |
| `gpuCoeff_saturates_high/low` | i8 範囲外は clamp される |
| `fullCoeff_exact` | 64 i16 なら全係数が保存される |
| `float_div16_ne_shift_for_negative` | 負の非 16 倍数で `/16.0` と `>>4` が一致しない |
| `saturation_changes_value` | i16 飽和は値を変える |
| `padded_stride_injective` | stride 9 は 32 bank で conflict-free |
| `unpadded_stride_not_injective` | stride 8 は conflict する |
| `pair_fusion_halves_loads` | 16×8 tile の読み出し 512 → 256 |
| `full_fusion_quarters_loads` | 512 → 128（4 分の 1） |

Lean では証明していないこと:

- GPU シェーダのコンパイラ挙動（register spill、 occupancy、命令選択）
- 実行時間
- bitstream 仕様全体との等価性（CPU の C 的 i32 wrapping や浮動小数の丸めを
  完全にモデル化していない）
- DC-only broadcast と full IDCT の差分（実験の differential test で確認）

この分担は Lean の本来の使い方である。Lean に「どこを速くするか」を探させるのではなく、
**候補の書き換えが意味を保存することを証明する**ために使う。

## 7. 優先順位つき提案

### P0（正確性・API）

1. **decode の非可逆性を明示**し、`Fast` / `Exact` を選べる API にする。
   Exact は 132 B パック + 整数 IDCT + DC フラグ。実験で 0 diff を確認済み。
2. **アダプタ依存の自動選択**を入れる。内蔵 GPU / 小解像度 / CPU デバイスでは
   CPU 経路を既定にし、離散 GPU でテクスチャが GPU 上にある場合だけ GPU を使う。
3. encode の byte-exact 回帰テスト（`assert_eq!`）を追加する。

### P1（測定済みの速度改善）

4. decode: shared memory stride 9、行テーブル hoist、32 スレッド出力。
   **-20 %（3.01 → 2.42 ms）**、PSNR 同一。
5. encode: FTAB/ZIGZAG の定数化、配列削減、`fdct_ya` / `fdct_uv` 統合。
   **opaque -22 %、alpha -31 %**、PSNR 100 dB。
6. encode: 16×8 macroblock 全融合（読み出し 4 分の 1）。次の大きな一手。
7. encode/decode の ring + async submit/finish で CPU Golomb と GPU を重ねる。

### P2（追加の最適化・運用）

8. hybrid pack（32 B + 高 AC tail）。q95 で 48 % の block だけ tail。
9. encode matrix の uniform/shared 化、係数の vector load/store。
10. texture/view/bind group/pipeline のキャッシュ、device 変更検出。
11. readback の wait 1 回化、preview 経路の整理、8K limits、sRGB の文書化。
12. `GpuStats` と CI（release の `settle_q`）。

## 8. 参考: 実験に使った変更の要点

### decode の正確版パック

```text
1 block = 132 byte
  0..127 : 64 × i16（zigzag scan order）
  128..131: u32 flag
            0 = 通常の IDCT
            1 = CPU の broadcast_dc を使う block（AC が全部 0）
```

- `decode_plane_coeffs` は `valid = terms_to_decode < 64` を block 先頭で記録。
- シェーダは flag が 1 なら `(dc + 4) >> 3 + add_val` を 8×8 に展開。
- それ以外は CPU と同じ i16 飽和 + `>>11` / `>>6` の整数 IDCT。
- CPU の `decode_plane_scalar` は `valid` で `broadcast_dc` を選ぶので、
  これで 0 diff になる。

注: CPU の `broadcast_dc` は `dc.wrapping_add(4)` と `wrapping_add(add_val)` を
使う。i16 の端まで厳密に合わせるなら、この 2 箇所も WGSL の i32 飽和ではなく
16 bit wrap（`(x << 16) >> 16`）で実装する。自然画像の実測では差は出なかったが、
仕様として 0 diff を保証するなら必要である。

### encode の全融合（疑似コード）

```wgsl
@compute @workgroup_size(64)
fn encode_tile(@builtin(local_invocation_index) lid: u32,
               @builtin(workgroup_id) wid: vec3<u32>) {
    // 1. 64 threads で 16x8 = 128 pixel を 2 pixel ずつ load
    //    Y/U/V/A を shared memory に展開（U/V は 2 pixel の平均）
    // 2. barrier
    // 3. 6 block（Y0,Y1,U,V,A0,A1）を 8 threads ずつで
    //    column pass -> shared transpose -> row pass -> quant -> zigzag
    // 4. 8 threads/block で 32 word を vector store
}
```

読み出しは 512 → 128、dispatch は 4 → 1。shared memory は
`Y:16×8`, `U:8×8`, `V:8×8`, `A:16×8`, `tmp:6×64`, `zig:6×64` で約 4.5 KB。

### アダプタ選択（疑似コード）

```rust
let info = adapter.get_info();
let prefer_cpu = matches!(info.device_type, wgpu::DeviceType::IntegratedGpu | wgpu::DeviceType::Cpu);
let gpu_resident = /* caller already owns the texture on this device */;
if prefer_cpu && !gpu_resident {
    // CPU decode/encode
} else {
    // wgpu path
}
```

M3 の実測では、1080p でも 4K でも CPU が勝つ。L4 では「CPU+transfer」に対して
GPU が勝つが、host CPU 単体には負ける。したがって「GPU 上に既にあるテクスチャを
そのまま使う」ことが GPU 経路の主な価値である。
